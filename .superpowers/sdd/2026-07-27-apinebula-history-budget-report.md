# APINebula 第四阶段历史预算修复报告

## 范围

- 仅修改内容矩阵 Agent 的 APINebula 文案生成请求。
- 未修改其他 8 个 Agent、诊断表单、阶段确认链、取消与过期响应保护。
- API Key 仍只存在当前页面内存；诊断过程没有输出、记录或写入 Key。

## Phase 1 证据

通过“新媒体图文生成器”的既有配置加载代码间接发起最少量诊断调用，只记录状态、耗时和长度：

| 请求 | 结果 |
| --- | --- |
| 固定连通性探针，`max_tokens=32`，180 B | HTTP 200，4.05 秒 |
| 阶段型长文，`max_tokens=3800`，2523 B | HTTP 503，0.45 秒 |
| 短提示，`max_tokens=3800`，182 B | HTTP 200，2.66 秒 |
| 第四阶段形态，两段历史，`max_tokens=2000`，5024 B | HTTP 200，90.58 秒，返回 6149 字符 |
| 第五阶段形态，三段历史，`max_tokens=3000`，7912 B | 110.47 秒后远端断开 |

代码追踪确认：

- 第四阶段点击只提交一次请求。
- `history` 顺序正确，为第二、第三阶段完整 Markdown。
- `confirmedStage=3`，没有跳阶段或越界。
- 用户错误为 `PROVIDER_UNAVAILABLE`，不是鉴权、限流或本地 180 秒超时。

## 单一根因

APINebula 请求此前在所有阶段固定声明 `max_tokens=3800`。第二、第三阶段之后，请求又携带完整历史，输入负载与声明的输出预算共同升高；上游会对这类长文请求即时返回 503 或在较高预算下断开。连接探针成功不能证明历史型长文请求可用。

## 最小修复

- 第二、第三阶段（历史少于两段）保持参考项目的 `max_tokens=3800`。
- 第四、第五阶段（历史达到两段）使用实测成功的 `max_tokens=2000`。
- 不截断、不摘要、不删除任何阶段历史。
- 不增加无证据的自动重试，避免重复计费。
- 第五阶段仍经过原有完整 Markdown 结构校验；若输出不完整，不会生成下载文件，并保留安全重试入口。

## 验证

- 新增 RED：第四阶段原实现返回 3800，期望 2000。
- 新增 RED：第五阶段原实现返回 3800，期望 2000。
- 定向测试：第四、第五阶段预算、完整历史和正式方案结构均通过。
- 完整验证：`npm test` 87/87 通过（包含生产构建）。
- `npm run lint` 通过。
- `git diff --check` 通过。

## 风险说明

APINebula 没有在当前证据中公开该代理模型的精确上下文/计算阈值，因此不能把 2000 描述为供应商保证值。它是本次用相同令牌、URL 和模型实测可完成第四阶段且返回 6149 字符的保守预算；正式方案的完整性仍由现有结构校验兜底。
